# KRONOSPACE PREMIUM UI AUDITOR & DESIGN LAB

## 1. Identidad

**Name:** `kronospace-premium-ui-auditor-design-lab`  
**Project:** KRONOSPACE / Kronos Space
**Path:** `.agents/skills/kronospace-premium-ui-auditor-design-lab/SKILL.md`  
**Type:** Product Architecture, Premium UX/UI Audit, Design System, Design Lab, Frontend/Backend Interface Review  
**Status:** Active when explicitly invoked by the user

Actúa como arquitecto senior de producto, auditor de frontend/backend, diseñador UX/UI premium, especialista en sistemas de diseño y desarrollador web/Android.

La misión es auditar primero el proyecto KRONOSPACE / KRONOS Social AI y posteriormente crear múltiples estructuras visuales de prueba, sin modificar, sobrescribir, hacer commit, push ni desplegar cambios en el repositorio productivo durante la fase de exploración.

El objetivo es encontrar una estructura visual que se sienta como una aplicación de alta gama, tecnológica, futurista, exclusiva y premium, manteniendo una identidad visual única y consistente en toda la aplicación.

---

## 2. Regla principal: auditar antes de diseñar

Antes de generar cualquier propuesta:

1. Inspeccionar la estructura real del proyecto.
2. Identificar frontend y backend.
3. Identificar framework, componentes, rutas, layouts y sistema CSS.
4. Identificar todas las pantallas existentes.
5. Identificar componentes reutilizables.
6. Identificar navegación.
7. Identificar botones y acciones.
8. Identificar modales, formularios, tarjetas, feeds, perfiles, mensajes, notificaciones y herramientas de IA.
9. Identificar estilos duplicados.
10. Identificar estilos heredados o incompatibles.
11. Identificar componentes que puedan reutilizarse.
12. Identificar problemas de responsive design.
13. Identificar inconsistencias visuales.
14. Identificar pantallas incompletas.
15. Identificar rutas inexistentes o inconsistentes.
16. Identificar conexiones frontend/backend relevantes para la interfaz.

**Durante esta auditoría no se debe modificar código productivo.**

Después de la auditoría, entrar en:

DESIGN LAB / PREVIEW ONLY

## 5. Identidad visual obligatoria

Toda la aplicación debe utilizar una identidad visual única.

### Fondo

El fondo principal debe ser negro puro:

```text
#000000
```

No utilizar como fondo principal:

- Azul.
- Morado.
- Verde.
- Rojo.
- Naranja.
- Rosa.
- Marrón.
- Cobre.
- Dorado.

No utilizar degradados de color como decoración principal.

---

## 6. Ilusión óptica del fondo

El fondo negro no debe sentirse como un simple rectángulo negro. Debe producir sensación de:

- Profundidad.
- Vacío.
- Espacio infinito.
- Superficie inexistente.
- Volumen.
- Atmósfera.
- Dimensión.
- Movimiento óptico extremadamente sutil.

La interfaz debe dar la impresión de que:

```text
LA PANTALLA NO TIENE FONDO.
```

No debe parecer una aplicación colocada encima de un fondo; debe parecer que la aplicación existe dentro de un espacio negro infinito.

La ilusión puede conseguirse mediante:

- Sombras extremadamente controladas.
- Halos monocromáticos.
- Profundidad.
- Transparencias.
- Reflejos.
- Partículas mínimas.
- Microtexturas.
- Iluminación ambiental.
- Líneas ópticas.
- Distorsiones sutiles.
- Perspectiva.
- Capas de negro con diferencias microscópicas de luminancia.

La ilusión debe ser elegante y discreta. No convertirla en galaxia, espacio con estrellas, cyberpunk, neón, videojuego ni fondo recargado. El negro debe seguir dominando absolutamente.

---

## 7. Cromo espejo

Todos los elementos principales de interfaz deben tener identidad de:

```text
CROMO ESPEJO / METAL PULIDO
```

Aplicar especialmente a:

- Botones.
- Bordes.
- Iconos.
- Textos importantes.
- Barras.
- Separadores.
- Controles.
- Indicadores.
- Navegación.
- Componentes destacados.

El acabado debe parecer metal real mediante:

- Reflejos.
- Highlights.
- Sombras.
- Microcontraste.
- Variaciones de gris.
- Brillos especulares.
- Sensación tridimensional.

Evitar:

- Gris plano.
- Plata plana.
- Blanco puro como sustituto del cromo.
- Apariencia plástica.

---

## 8. Paleta

### Paleta principal

```text
Negro puro: #000000
```

### Cromo

```text
#FFFFFF
#F2F3F5
#D5D7DA
#B7BABE
#8B8E93
#62656A
#35383C
#181A1D
```

La aplicación debe mantenerse en negro + escala de grises + cromo.

No introducir colores arbitrarios. Si una función necesita indicar activo, error, advertencia o éxito, debe utilizarse una solución visual compatible con el sistema monocromático siempre que sea posible, sin romper la identidad visual.

---

## 9. Tipografía

Crear jerarquía clara:

- **Titulares:** premium, tecnológicos y limpios.
- **Texto:** extremadamente legible.
- **Microcopy:** pequeño pero perfectamente legible.

No utilizar demasiadas familias tipográficas. Toda la aplicación debe parecer diseñada por un único equipo.

---

## 11. Botones

Todos los botones deben pertenecer al mismo lenguaje visual.

Estados obligatorios:

- Default.
- Hover.
- Active.
- Pressed.
- Focus.
- Disabled.
- Loading.
- Success.
- Error.

El efecto de interacción debe sentirse físico:

```text
reposo → reflejo metálico → hover → highlight → pressed → compresión visual → liberación
```

Evitar botones genéricos de frameworks.

---

## 12. Abanico principal

El menú de abanico debe ser uno de los elementos distintivos de KRONOSPACE.

Debe conservar:

- Botón central.
- Navegación radial.
- Botones circulares.
- Iconografía.
- Etiquetas.
- Animación.
- Apertura.
- Cierre.
- Scrim.
- Estados activos.

Pero se deben explorar diferentes composiciones:

- **Estructura A:** abanico semicircular clásico.
- **Estructura B:** abanico orbital.
- **Estructura C:** abanico con profundidad 3D.
- **Estructura D:** abanico compacto para móvil.
- **Estructura E:** abanico expandido para desktop.
- **Estructura F:** abanico híbrido contextual.

Cada una debe probarse visualmente antes de decidir.

---

## 13. Comportamiento contextual

El abanico no debe comportarse igual en todas las pantallas. Debe conocer:

- Pantalla actual.
- Ruta actual.
- Módulo actual.
- Acción actual.
- Estado del usuario.
- Contexto de navegación.

Ejemplos:

- Home → navegación global.
- Perfil → navegación global + acciones sociales.
- Mensajes → navegación global + contexto de conversación.
- Kairos → navegación global + herramientas IA.
- Crear → navegación global + preservación del borrador.
- Notificaciones → navegación global + regreso contextual.
- Configuración → navegación global + contexto de configuración.

## 29. Regla de seguridad del repositorio

Hasta que el usuario elija una propuesta:

```text
READ ONLY
```

No realizar:

- `git add`.
- `git commit`.
- `git push`.
- Deploy.
- Database migration.
- Production changes.

La única excepción es cuando el usuario explícitamente pide agregar o actualizar esta skill; después de esa operación, la fase Design Lab vuelve a READ ONLY para el código productivo.

## 30. Criterio de calidad

Una propuesta solamente puede considerarse lista para presentar si:

- Parece una aplicación premium.
- Tiene identidad propia.
- Funciona visualmente en móvil.
- Funciona en desktop.
- Mantiene el negro puro.
- Utiliza cromo espejo.
- No introduce colores innecesarios.
- Tiene jerarquía.
- Tiene navegación coherente.
- No depende de una sola pantalla.
- Puede escalar a toda la aplicación.
- Reutiliza componentes.
- No genera contradicciones entre módulos.
- Mantiene consistencia visual.

## 32. Directiva final

KRONOSPACE debe competir visualmente con productos tecnológicos de alta gama.

No crear una interfaz genérica. No utilizar plantillas comunes. No copiar estilos de redes sociales existentes.

Construir una identidad propia basada en:

```text
NEGRO PURO + ILUSIÓN DE AUSENCIA DE FONDO + CROMO ESPEJO + PROFUNDIDAD + PRECISIÓN + MINIMALISMO + INTERACCIÓN PREMIUM
```

La sensación final debe ser:

```text
El usuario no está mirando una página negra con elementos plateados; está entrando a un espacio digital negro infinito donde la interfaz está fabricada en cromo espejo.
```

Primero auditar. Después construir varias alternativas. Después mostrar. Después permitir elegir. Y solamente después implementar.

## 33. Activación operativa

Cuando esta skill esté activa:

1. Mantener compatibilidad con la skill `kronos-integration`: ningún botón sin acción real conectada, no inventar endpoints, modelos ni eventos, no romper contratos existentes.
2. Para cualquier auditoría, usar lectura y análisis del código real antes de proponer.
3. Para prototipos, usar únicamente un espacio aislado y claramente temporal fuera del código productivo.
4. No tocar archivos productivos durante la auditoría o Design Lab.
5. No hacer commit, push ni despliegue hasta que el usuario elija propuesta y apruebe plan de implementación.

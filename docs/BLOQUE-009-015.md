## 2. BLOQUE 009 — búsqueda global

### Contrato

`GET /api/search?q=<texto>&scope=all|users|posts&page=&limit=` requiere sesión.

- `q` se recorta, exige 2–80 caracteres y se escapa antes de crear la regex.
- `limit` es 1–30 (15 por defecto); la respuesta conserva `page`, `limit`,
  `totals` y `hasMore` por tipo.
- `scope=all` devuelve ambos arrays; `users` o `posts` evita la consulta no
  requerida.
- Personas: excluye al solicitante, no muestra cuentas no descubribles, aplica
  exclusión de bloqueo en ambos sentidos y devuelve la proyección `publicUser`.
- Publicaciones: reutiliza `feedConstraints`, por lo que respeta bloqueos,
  silencios, publicaciones ocultas y moderación global; se normalizan con el
  contrato público existente.

`UserSearch` consume `searchGlobal` de `usersService` y muestra ambos tipos de
resultado. La prueba heredada se actualizó para representar el nuevo contrato
sin perder la comprobación de que un contador privado no se convierte en cero
tras seguir a una persona.

## 3. BLOQUE 010 — herramientas AI y scripts

`client/src/services/aiService.js` es la única capa de dominio para las rutas
AI: imágenes, vídeo, jobs, scripts/proyectos e interacción con KAIROS. Todos
los componentes AI activos consumen esa capa; `apiClient.js` sigue siendo el
único lugar del frontend que importa Axios.

- Imagen: `style` admite `cinematic`, `editorial`, `concept-art` y
  `photorealistic`; `negativePrompt` se persiste y valida. El servidor compone
  ambos para el proveedor, sin reemplazar el prompt original del usuario.
- Vídeo: se conservó el polling que ya existía en `VideoJobs`; solo se
  centralizó la integración HTTP. **No se reimplementó polling.**
- Guiones: `ScriptGenerator` genera, carga historial, reutiliza, elimina,
  edita estructura y crea proyectos mediante el servicio común.
- Historial, biblioteca y chat KAIROS abandonan instancias Axios locales.

No se llama a un proveedor AI durante la prueba automática: la validación
unitaria comprueba la composición determinista del prompt y el build comprueba
las importaciones del cliente.

## 4. BLOQUE 011 — sesiones y preferencias

### Dispositivos

Los access tokens nuevos incluyen `sid`, el `familyId` de su refresh token.
Para un JWT con `sid`, `auth` comprueba que la familia siga activa: una
revocación selectiva corta de inmediato ese access token (`401
SESSION_REVOKED`), no solo el próximo refresh. El handshake Socket.IO aplica
la misma verificación y las conexiones vivas de esa familia se desconectan al
revocarla. Los JWT históricos sin `sid` permanecen compatibles hasta expirar.

| Ruta | Efecto |
|---|---|
| `GET /api/auth/sessions` | Lista familias activas del usuario sin hashes ni tokens. |
| `DELETE /api/auth/sessions/:familyId` | Revoca una familia que pertenece al usuario. |
| `DELETE /api/auth/sessions` | Cierra todas, o todas excepto la actual con `{ "exceptCurrent": true }`. |

`Settings` muestra sesiones, permite cerrar una o las demás y ejecuta el
logout de la SPA si se cerró la familia actual.

### Preferencias

`PATCH /api/users/me/preferences` persiste exclusivamente para el usuario de
la sesión: `notifications.inApp`, `notifications.email`,
`content.showSensitive`, `appearance` y `language`. Los valores por defecto
mantienen el comportamiento previo. Por ahora solo `inApp` tiene efecto de
backend: evita crear notificaciones in-app nuevas; correo y filtrado sensible
se almacenan sin simular funcionalidades inexistentes.

## 5. BLOQUES 012–013 — feedback, accesibilidad y administración

- `ToastProvider` ofrece feedback global y región `aria-live`; el interceptor
  de sesión informa cuando un 401 termina la sesión.
- `OfflineNotice` responde a los eventos nativos `online`/`offline`.
- `AppLayout` incorpora “Saltar al contenido principal” y
  `<main id="main-content" tabIndex="-1">`.
- El CSS añadido cubre toast, conectividad, sesiones, ajustes admin y
  `forced-colors`, sin reemplazar el sistema de diseño previo.

`requireAdmin` consulta el rol vigente de `User` en MongoDB, no un claim del
JWT. La misma protección reemplaza el guard duplicado de moderación. Bajo
`/api/admin`, un administrador puede consultar resumen, buscar/listar usuarios
paginados, cambiar roles válidos de terceros y revisar posts recientes. No
puede cambiarse su propio rol. `AdminCenter` se expone en `/admin` y solo se
ofrece desde Settings cuando el usuario tiene rol administrador.

## 6. BLOQUES 014–015 — calidad, seguridad y operación

### Paso revisado sin modificar comportamiento de producto

BLOQUE 014 no reescribe el cliente HTTP ni el polling ya existentes: se revisó
la consolidación y se añadió una garantía automática mínima. `npm run lint
--workspace=client` ejecuta ESLint con:

1. `react-hooks/rules-of-hooks`; y
2. una restricción que prohíbe importar `axios` en `client/src`, salvo en
   `client/src/services/apiClient.js`.

La CI ejecuta este lint antes del build. Esta es una **revisión con garantía**,
no una reimplementación de API ni de UX.

### Observabilidad segura

`requestContext` acepta un `X-Request-Id` alfanumérico y acotado o genera un
UUID; siempre devuelve el header de respuesta. El servidor acumula métricas
solo en memoria por proceso, por clase HTTP. `GET
/api/observability/summary` requiere usuario y rol admin.

Los logs de error estructurados guardan ID, método, ruta y estado; no incluyen
cuerpo, `Authorization`, token, secreto ni refresh token. `TRUST_PROXY` queda
desactivado por defecto; `true` o `1` habilita únicamente un proxy conocido.
Las variables se documentaron en ambos archivos de entorno de ejemplo y
`kronos-doctor` las reconoce.

## 7. Verificación y límites conocidos

### Comandos ejecutados localmente

```bash
npm ci
npm run lint --workspace=client
npm test --workspace=server
npm test --workspace=client
npm run build --workspace=client
node scripts/kronos-doctor.js
```

Resultado local de cierre:

- cliente: **47 pruebas aprobadas** (15 Node + 32 Vitest), lint sin errores y
  build correcto (1729 módulos); Vite informa un chunk JS de 504.92 kB, sin
  fallar el build;
- servidor sin Mongo configurado: **76 pruebas**, 33 aprobadas, 43 omitidas,
  0 fallos; las 4 comprobaciones de contrato nuevas cubren parser de búsqueda,
  prompt AI, `sid` y request IDs/rutas protegidas;
- `server/test/block-009-015.e2e.test.js` añade 3 escenarios de MongoDB real:
  discovery antes/después de bloquear, preferencias + revocación de dispositivo
  y admin/observabilidad. Localmente se omiten de forma explícita sin
  `MONGODB_URI`; nunca usan memoria ni una base ficticia.
- `kronos-doctor` falla como corresponde en este entorno porque no hay
  `MONGODB_URI`, `JWT_SECRET` ni `CLIENT_URL`; no se interpretó como una
  verificación de producción.

El workflow **Kronos E2E (MongoDB real)** corre todas las suites `*.e2e.test.js`
contra `mongo:7` en una base temporal `kronos_e2e_<aleatorio>` y, si existe el
secreto, contra Atlas en otra base temporal. La verificación de despliegue y
el resultado de CI se registran tras abrir el PR; no se anticipan como
completados en este documento.

## 8. Fuera de alcance deliberado

- No se creó un simulador de email ni se afirma que la preferencia de correo
  envíe mensajes.
- No se añadió persistencia externa de métricas ni logging de cuerpos: hacerlo
  violaría el límite de seguridad del bloque.
- No se ejecutó un proveedor AI de terceros durante test automático.
- No se alteraron componentes o contratos duplicados ya cerrados; el polling
  de vídeo y los flujos sociales existentes solo fueron revisados o adaptados
  a la capa HTTP común cuando era necesario.

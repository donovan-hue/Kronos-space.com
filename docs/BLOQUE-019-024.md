## 2. 019 — adjuntos

- `POST /api/messages/media/upload` (multipart, campo `media`): **mismo
  contrato** que `POST /api/posts/media/upload` (AUDIT-005):
  respuesta `201 { url, mimeType, size }` con `url` en `/uploads/media/…`.
- `Message.media` (subdocumento `{ url, mimeType, size, alt }`) nuevo y
  opcional. Validación única en `messages/messageMedia.js`:
  - solo URLs de `/uploads/media/` generadas por el propio pipeline
    (rechaza otros subdirectorios, URLs externas y trampas de ruta);
  - solo jpg/png/webp; 0 < size ≤ 10 MB; alt ≤ 500.
- `POST /api/messages/:userId` y `POST /api/conversations/:id/messages`
  aceptan `media` opcional; texto y media son **alternativos** (uno de los
  dos basta; sin ninguno sigue siendo 400, mismo mensaje que antes).
- Lista de conversaciones: `latestMessage.hasMedia` (booleano derivado).
- Cliente: composer compartido con botón adjuntar, preview, alt opcional y
  quitar; la burbuja muestra la imagen con su alt.

## 3. 020 — presencia y typing

- Presencia **en memoria** por instancia (`messages/presence.js`):
  `Map<userId, Set<socketId>>`. Al entrar en línea el servidor emite
  `presence:changed { userId, online: true }` a todos; igual al salir.
- REST: `GET /api/messages` añade `user.online`; `GET /api/messages/:userId`
  añade `online`; `GET /api/conversations/:id/messages` añade `online` por
  miembro. Es mejora opcional: sin socket la UI funciona igual.
- Typing: `typing:start { peerId }` del socket → el servidor retransmite
  `typing:start { from }` **solo al peer** (sala `user:<peerId>`).
  Throttle: 2 eventos/segundo por socket (el resto se descarta). No hay
  persistencia de typing (es efemero por diseño).
- Cliente: punto de presencia en lista, chat y miembros de grupo;
  "Escribiendo…" 3 s; el composer avisa typing cada 3 s como máximo.

## 4. 021 — reintentos y estados

- `Message.clientMessageId` (≤128, índice parcial con `sender`): el cliente
  genera **un id por mensaje** y lo reutiliza en cada reintento. Si el
  backend ya tiene ese id para el mismo emisor y conversación, devuelve el
  mensaje original: `200 { message, deduplicated: true }` (nunca duplica).
- `Message.delivered` nuevo; `read` conserva su significado (AUDIT-004).
  Derivación del estado en la UI:
  - 1-a-1: `read` → Leído; `delivered` → Entregado; otro → Enviado.
  - Grupo: `readBy` con otro → Leído; `readBy` conmigo o `delivered` →
    Entregado; otro → Enviado.
- `PATCH /api/messages/:userId/delivered` (nuevo): el cliente lo invoca al
  abrir la conversación. `PATCH /:userId/read` (contrato anterior) ahora
  implica `delivered` también.
- Cliente: cola local de envío (`useMessageSend`); si el envío falla el
  mensaje queda "No se envió" con **Reintentar** (mismo `clientMessageId`)
  y **Quitar**. Un reenvío tardío de un envío que ya llegó también
  deduplica.

## 5. 022 — grupos

- Modelo `Conversation`: `name` (≤60, opcional), `members` (2-10, índice),
  `createdBy`. Las conversaciones 1-a-1 **no** usan este modelo (siguen en
  el par sender/receiver de `Message`, contrato AUDIT-004 intacto).
- `Message.conversation` (ref `Conversation`, nullable) y `Message.readBy`
  (lista de lectores; en 1-a-1 no se usa).
- Rutas (`/api/conversations`, con el limitador de abuso existente):
  - `POST /` `{ name?, memberIds[] }` → 201. Creador auto-incluido;
    2-10 miembros; usuarios inexistentes → 400 `USERS_NOT_FOUND`; mismo
    conjunto de miembros → 409 `CONVERSATION_EXISTS`.
  - `GET /` → mis grupos con `latestMessage` (incluye `hasMedia`) y
    `unreadCount` real (mensajes de otros que yo no leí).
  - `GET /:id/messages` → hilo (200, ascendente, 200 últimos) + miembros
    con `online`. No miembro → 403 `CONVERSATION_NOT_MEMBER`.
  - `POST /:id/messages` → mismas reglas de contenido que 1-a-1 (019/021)
    y emisión a la sala `conversation:<id>`.
  - `PATCH /:id/read` → `readBy += yo` en los mensajes de los demás y
    `delivered`.
  - `PATCH /:id/members` `{ add, remove }` → solo creador (403
    `NOT_CREATOR`); ya miembro → 409 `MEMBER_EXISTS`; creador no se quita
    (400 `CREATOR_LOCKED`); límites 2-10 (400 `MEMBER_COUNT`).
  - `DELETE /:id` → solo creador.
- Socket: `conversation:join { conversationId }` → el servidor **verifica
  membresía en base** antes de entrar a la sala; sin membresía responde
  `conversation:error { code: "CONVERSATION_NOT_MEMBER" }`.
  `conversation:leave` sale de la sala.
- Cliente: `/conversations` (lista + creación con búsqueda de usuarios) y
  `/conversations/:id` (hilo con los mismos componentes que 1-a-1:
  `MessageList`, `MessageComposer`, `useMessageSend`). Gestión de miembros
  visible solo para el creador.

## 6. 023 — catálogo de notificaciones

- `Notification.NOTIFICATION_TYPES` es la única definición del catálogo
  (`follow, like, comment, repost, save, moderation`); el modelo lo usa como
  `enum` y la ruta lo valida para filtros.
- Cada tipo existente tiene su frase en la UI (antes repost/save/moderation
  caían en un genérico).
- Un bloqueo sigue suprimiendo notificaciones (contrato 011; aquí se
  verifica el efecto sobre notificaciones).
- `save` está en el catálogo para uso futuro; hoy no se emite.

## 7. 024 — filtros y paginación

- `GET /api/notifications?type=a,b&page=&limit=`:
  - `type` opcional, valores del catálogo; inválido → 400 `INVALID_TYPE`;
  - `page` ≥ 1, `limit` 1-100 (default 30);
  - respuesta: `{ notifications, unreadCount, page, limit, total, hasMore }`
    (el contrato original `{ notifications, unreadCount }` se conserva;
    `unreadCount` sigue siendo el total de no leídas **sin** filtro).
- UI: chips de filtro (Todas/Seguidos/Me gusta/Comentarios/Republicaciones/
  Moderación) y "Cargar más" con `hasMore`.

## 9. Compatibilidad y seguridad

- El contrato 1-a-1 de AUDIT-004 se conserva: los endpoints anteriores
  siguen existiendo con sus respuestas; solo **se añaden** campos
  (`online`, `delivered`, `hasMedia`) y `clientMessageId` es opcional.
- `receiver` deja de ser obligatorio en `Message` (los mensajes de grupo lo
  dejan en null); los mensajes 1-a-1 siempre lo llevan, como antes.
- Los adjuntos solo aceptan URLs producidas por el propio upload
  (mismo criterio que posts, AUDIT-005): no hay rutas arbitrarias ni
  subdirectorios ajenos; el middleware de firma real no se toca.
- `clientMessageId` no es secreto: solo deduplica por emisor. El índice es
  parcial (solo mensajes con id).
- La presencia no expone nada más que "en línea / no" (público, como en las
  plataformas existentes); typing no se emite a terceros.

## 10. Pendientes honestos

- **Presencia multi-instanza**: la presencia vive en memoria de cada
  proceso de servidor. Con Render (una instancia) es correcto; con varias
  instancias habría que compartir el estado (Redis o similar).
- **Typing solo 1-a-1**: en grupos no hay typing (solo presencia por
  miembro).
- **Salas de socket tras reconexión**: el cliente vuelve a pedir la sala al
  reconectar mientras está en el hilo; al recargar la página el estado se
  repone desde la API.
- **Eliminar grupo** no borra sus mensajes (quedan en base sin conversación
  accesible; nadie puede listarlos).
- **Notificaciones por mensaje**: no se crean notificaciones por cada
  mensaje privado (ruido); queda fuera del alcance declarado.
- Persistencia de `uploads/` en Render y QA en navegador real: vigentes
  desde bloques anteriores (BLOQUE 007-016 §8).
